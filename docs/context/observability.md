# Observability

## Purpose

Defines Audit (historical operational traceability), Metrics
(measurable operational information), and Suggestions (non-authoritative
recommendations) — the three ways OrchAI reports on what happened
without ever controlling what happens next.

## Objective

Give every protected operation a traceable record, every AI-usage
number a clear authoritative source, and every "what should happen
next" idea a status that can never be confused with a decision.

## Current Status

`implemented`

## Audit

Preserves the operational history needed to understand what OrchAI
did, why, and under which authorization/execution conditions. Covers
Task, State Transition, Authorization, Context, Execution, Model,
Event, User Decision, Suggestion, Error, Retry, Resource Usage, and
Project Change — plus, where applicable, Project Readiness, Security
Profile, Persistence Scope Change, Provider-Sharing Decision, Git
Initialization, and CI/CD Enablement. A record carries unique
identity, timestamp, actor, operation, task, project, execution,
authorization, correlation information, outcome, and relevant
metadata. Records are append-oriented: corrections are additional
records or events, never silent rewrites.

## Metrics

Measurable operational information about orchestration, execution,
models, projects, and workflow behavior: token usage, execution
duration, model usage, local vs. cloud usage, estimated cost,
success/failure/retry rate, task completion time, suggestion
acceptance rate. Derived only from authoritative records (Execution,
Audit, Events, Task Lifecycle, Authorization) — the UI is never the
source of truth. May be grouped by task/project/role/action/model/
provider/execution mode/time period/outcome. `ESTIMATED COST ≠
INVOICED COST` — estimated values stay identifiable as estimates.
Metrics never change task state, and must never silently count
suggestions as executions, rejected authorizations as executions,
failed event deliveries as completed operations, or retries as
replacements for previous attempts. `MetricsRepository.summarize()`
computes count/sum/avg per metric name grouped by any combination of
those dimensions over an optional time window, exposed via `GET
/metrics/summary` / `orchai metrics summary`.

## Suggestions

An optional recommendation generated by OrchAI — supports
decision-making but never authorizes or executes anything. May
consider task state, workflow configuration, role, action, model
capabilities, project configuration, execution history, metrics,
resource availability, and previous findings. A suggestion identifies
the suggested action, rationale, related task/execution, required
capabilities, expected impact, authorization requirement, and
confidence/priority when supported. Lifecycle: `GENERATED → PRESENTED
→ ACCEPTED / REJECTED / EXPIRED`; acceptance never bypasses
authorization. A `PLANNED` task suggests `DEVELOPER`+`IMPLEMENT`; an
`IMPLEMENTED` task suggests `QUALITY_AGENT`+`REVIEW`. In `MANUAL` mode
suggestions may be limited or disabled; in `SUGGESTED` mode the user
decides; in `AUTOMATIC` mode a suggestion leads to execution only when
existing policy already authorizes that operation.
`SuggestionEngine.suggest_next()` reuses an existing `PRESENTED`
suggestion matching the task's current `(role, action)` instead of
duplicating it, and ignores a stale `PRESENTED` suggestion left over
for an already-superseded stage (see ADR-011).

## Component Ownership

- **Audit Manager** — maintains authoritative orchestration history; records task lifecycle, events, state transitions, authorization requests/decisions, executions, selected role/action/model, context references, results, errors, configuration changes. Must not modify workflow state as a side effect of recording. Maps to `infrastructure/observability/` (application coordination alongside the domains it records).
- **Metrics** — collects measurable system/AI usage information for operational monitoring, optimization, auditing, user decisions, and suggestion generation. Does not directly control execution.
- **Suggestion Engine** — generates optional recommendations from task state, configuration, execution history, available models, project configuration, metrics, and audit information. Must not execute suggestions directly in `SUGGESTED` mode, reinterpret a suggestion as authorization, or silently modify task configuration. Maps to `application/suggestions/`.

## Key Rules

- significant protected operations, authorization decisions, and execution attempts are always auditable; audit failures must never silently erase the operation that should have been recorded
- metrics derive only from authoritative information; retries remain individually measurable; estimated values are always identified as estimates
- suggestions are non-authoritative and never change task state or execute operations by themselves; accepted suggestions remain subject to authorization

## Main Relationships

- consumes every event from `Events And State` and every decision from `Authorization Policy`
- reports on `Tasks And Lifecycle` and `Execution Engine` activity
- exposed through `Chat-First And Interfaces` (`/audit`, `/metrics`, `/suggestions`, and `GET /requests/{id}/flow`)
